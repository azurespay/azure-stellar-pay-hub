## Findings fixed

### C-1 — Critical: a Redis outage crashed the API process

**Symptom.** With Redis stopped, `/api/health/ready` returned HTTP `500`
(`{"statusCode":500,"code":"INTERNAL_ERROR"}`) and — worse — the Node process **exited**
(container `Exited (1)`), taking every in-flight request with it.

**Cause.** Two compounding bugs:

1. `RedisThrottlerStorage.increment` (`apps/api/src/infra/redis-throttler.storage.ts`) awaited
   `redis.eval(...)` with no error handling. The throttler guard runs **before every
   controller**, so an ioredis `MaxRetriesPerRequestError` propagated as a non-HTTP exception
   and the global filter rendered it as a `500` — meaning `/api/health/ready` never reached
   its own (correct) `503 degraded` branch.
2. ioredis rejects pending commands when the retry budget is exhausted; Node's default turns an
   unhandled rejection into a fatal exception, so the process died.

**Fix.**

- The throttler storage now **fails open**: on a Redis error it logs once, reports
  `isBlocked: false`, and lets the request through. Redis is a protective dependency, not a
  correctness one — an outage must not become "every endpoint returns 500".
- `apps/api/src/main.ts` registers `process.on('unhandledRejection', …)` so a soft-dependency
  rejection is logged rather than fatal. Only rejections are intercepted; a synchronous
  `uncaughtException` still crashes as it should, so real bugs are not masked.

**Verified end-to-end** (production image, Redis stopped → restarted):

| Step                                | Before fix           | After fix                                                               |
| ----------------------------------- | -------------------- | ----------------------------------------------------------------------- |
| `/api/health/ready` with Redis down | `500` internal error | `503` `{"status":"degraded","checks":{"database":"up","redis":"down"}}` |
| `/api/assets` with Redis down       | `500`                | `200` (still serving)                                                   |
| Process                             | **killed** (exit 1)  | alive, uptime continuous (17s → 40s → 67s, no restart)                  |
| After Redis/RDS recovery            | n/a (dead)           | `200` `{"status":"ok"}`                                                 |

Postgres behaves correctly too: `503` with `database: down`, auth-protected routes fail
closed with `401` (no hang, no crash), and the same process recovers.

### C-2 — Critical: `pnpm build` failed for all four Next.js apps on the documented setup

**Symptom.** `pnpm build` exited 1 with `docs`, `web`, `admin` and `explorer` failing:

```
Error occurred prerendering page "/_global-error"
TypeError: Cannot read properties of null (reading 'useContext')
```

The README's Verification table claimed build **PASS**.

**Cause.** `.env.example` shipped `NODE_ENV=development`. The README's own Quick Start runs
`pnpm generate:env`, which copies it to the workspace-root `.env` — and **Nx loads the
root `.env` into every task**, so `next build` inherited `NODE_ENV=development`. Next.js
refuses to build in development mode (the `/_global-error` prerender fails). CI is green only
because CI never runs `generate:env`, so `NODE_ENV` is unset there. Proven by probe:
`NODE_ENV=production` makes the build pass; the shell itself has `NODE_ENV` unset.

**Fix.** Removed `NODE_ENV` from `.env.example` with a comment explaining why (Next/Nest set
it themselves for build/serve, and the config schema defaults it to `development`). Verified:
`pnpm build` → 17/17 projects, and a pristine clone with only this change builds green.

### H-1 — High: the documented env template produced a config that fails validation

**Symptom.** `pnpm test:unit` exited 1: `apps/api/src/common/routes.test.ts` failed to boot
`AppModule`, and any deployment copying `.env.example` verbatim would refuse to start:

```
ZodError: { "validation": "url", "path": ["IPFS_API_URL"], "message": "Invalid url" }
```

**Cause.** `.env.example` declares `IPFS_API_URL=` (intentionally blank). `dotenv`/Nx surface
that as `''`, which `z.string().url().optional()` rejects — `.optional()` only tolerates
`undefined`, not an empty string. An empty value here means "not configured", and
`ipfs.service.ts` already falls back to `http://127.0.0.1:5001/api/v0`.

**Fix.** Added an `emptyToUndefined` normalisation in `packages/config/src/schema.ts` applied
to the optional-URL and defaulted-URL fields, so blank means unset. Required secrets
(`JWT_SECRET`, `ADMIN_PASSWORD`, `WEBHOOK_SIGNING_SECRET`) are unaffected and still enforced.

### M-1 — Medium: inbound indexer hammered Horizon with an invalid address every cycle

**Symptom.** Every indexer cycle logged:

```
WARN [HorizonInboundService] { err: 'horizon payments HTTP 400',
  address: 'G6S2BSYXLKRDGNKK3BC74H7GXGX3QQRBM6S2BSYXLKRDGNKK3BC74H7G' }
```

**Cause.** The seed's `demoKey()` builds a 56-char string by cycling digest bytes
(`h[i % h.length]`), producing a repeated pattern that is **not a valid Stellar StrKey** (no
CRC16 checksum). The inbound listener polled the ACTIVE demo merchant's `settlementPublicKey`
regardless, earning a permanent Horizon `400`.

**Fix.** The listener now StrKey-validates each settlement key before polling, skips invalid
ones, and reports each once instead of once per cycle; a Horizon `404` (account not yet
funded) is treated as "no history yet" rather than a failure. Covered by two new unit tests
(and the existing fixtures were updated from fake to real StrKeys, since they are now validated).

### M-2 — Medium: production container retried a permanent error five times, then died cryptically

**Symptom.** Deploying the production image against a database that was created with
`pnpm db:push` (the documented local flow) produced `P3005 The database schema is not empty`,
retried 4 more times, then exited with no guidance.

**Cause.** Local dev uses `prisma db push` (no migration history); the container runs
`prisma migrate deploy`, which refuses to guess whether an unmanaged schema matches. The
retry loop treated this permanent condition as transient.

**Fix.** `infrastructure/docker/start.sh` now detects `P3005`, fails immediately, and prints
the exact one-time baseline commands. Documented in `docs/deployment.md` and the README.
Verified: the container still boots correctly against a migration-managed database
(5 migrations applied, `/api/health` ok, `/api/health/ready` `database: up, redis: up`,
`/api/assets` 200).

### L-1 — Low: the config package's test target was a silent no-op

`packages/config` declared `"test": "jest --passWithNoTests"` but shipped **no Jest config and
no Jest devDependency**, so it always passed with zero tests — leaving the boot-critical
environment schema completely uncovered (which is why H-1 reached `main`). Added the Jest
config/Jest devDeps and `packages/config/src/schema.test.ts` with 5 regression tests covering
blank optional URLs, blank defaulted URLs, the full blank-valued `.env.example` shape,
malformed non-empty URLs, and still-required secrets.

## Findings reported, not fixed

These need a decision or a contract redeploy, so they are documented rather than changed
silently.

1. **Contract storage layout does not scale (Medium-High, mainnet blocker).** All six contracts
   keep their collections in a single **instance-storage `Map`** (`DataKey::Escrows`,
   `DataKey::Withdrawals`, …). Every call deserialises and rewrites the whole collection, and
   `all_ids()` returns the entire key set with no pagination. Cost and ledger-entry size grow
   linearly with the number of escrows/invoices/subscriptions, so the contracts cannot scale
   past a modest size. The idiomatic fix is per-key **persistent** entries with paginated list
   functions — a storage-format change that requires new deployments and a migration.
2. **Escrows created without an expiry can lock funds forever.** `create(..., expiry: None)`
   stores `expiry = u64::MAX`, and `refund` requires `now > expiry`, so after `release_time`
   passes the initiator can never refund. If the counterparty (or arbiter) never calls
   `release`, the funds are stuck permanently. A timeout-based escape hatch (or requiring an
   expiry) is needed.
3. **Uniform short TTL.** Every path calls `extend_ttl(5000, 5000)` — roughly 7 hours of
   ledgers — and there is no `restore` helper. An idle contract's instance entry can be
   archived, and because all state lives in the instance entry, archival freezes the whole
   contract until restored. Per-contract TTL budgets are needed for production.
4. **Rate limiting now fails open while Redis is down** (C-1 fix). This is the deliberate
   availability trade-off; brute-force protection weakens during a Redis outage. If
   fail-closed is preferred for auth endpoints specifically, that is a policy decision.
5. **`infrastructure/kubernetes/secrets.yaml` ships placeholder `stringData`** inside the
   Kustomize bundle (so `secretKeyRef`s resolve). It carries a prominent warning, but a blind
   `kubectl apply -k` deploys known secrets; a `secretGenerator`/external-secret pattern would
   be safer.
6. **No frontend tests.** `apps/web`, `apps/admin` and `apps/explorer` have no test files, and
   `analytics`, `logger`, `notifications` and `types` are likewise uncovered (their
   `jest --passWithNoTests` targets pass trivially).
7. **Independent security audit not performed** — already acknowledged honestly in `SECURITY.md`.

## Security findings

The defensible posture is better than typical for this stage. The e2e security suite covers:
missing bearer token, forged/malformed JWT, revoked-session reuse, non-admin → admin endpoint
(`403`), cross-user IDOR/BOLA (`404`, no existence oracle), public-checkout CSRF carve-out,
and auth rate limiting (`429`).

**Verified positively (not merely claimed):**

- **Payment-amount manipulation** — the submit gate `verifySignedPaymentMatchesIntent`
  (`packages/sdk/src/stellar.ts`) genuinely enforces: exactly one payment operation, amount
  compared as **exact stroop integers** (so `$1`-for-`$50` and decimal-rounding tricks fail),
  recipient, asset code **and issuer**, and memo when the intent carries one; undecodable XDR
  is rejected. Directly unit-tested including the "$1-for-$50 attack".
- **_Unauthorized admin actions_** — global JWT guard + hierarchy-aware `@Roles('ADMIN')`,
  asserted at HTTP level (`403`).
- **Replay/duplication** — `ChainEvent.eventId` unique, `Transaction.hash` unique,
  `Idempotency-Key` `@@unique([userId, key])`, and a duplicate-delivery test proving no
  double-credit.
- **Contract authorization** — `require_auth` on every privileged path (payer, merchant,
  caller, and admin via `stored.require_auth()` with an equality check); treasury withdrawal
  requires membership, per-member approval, quorum, allowlist, cap and balance; idempotency
  flags (`released`/`refunded`/`executed`) prevent double-spend and replay.
- **No secrets in the repo** — no tracked `.env`, keys or credentials; only `.env.example`
  files and placeholder Kustomize secrets.

**Gaps (consistent with the repo's own threat model):**

- No independent/third-party audit (acknowledged in `SECURITY.md`).
- Rate limiting fails open during a Redis outage (C-1 trade-off, see above).
- No dedicated non-admin test for the contracts' admin `require_auth` path (the repo already
  tracks this gap honestly).
- The presented threats were not independently pen-tested; no DoS/load run was executed
  (`tests/load/payment-load.js` requires a k6 binary that is not installed here).

## Smart-contract & gas findings

**Verified.** All six contracts build to `wasm32v1-none` release (16.9–25.1 KB) and pass
**76 tests, 0 failed**. Reviewed `escrow`, `treasury` (and all `require_auth` sites, TTL calls
and panic paths across the workspace):

- `require_auth` on all 23 privileged call sites; checks are performed on the same value that
  is then authenticated, so argument spoofing fails.
- **No `unwrap()`/`expect()`/`panic!()` in production code paths** — errors are typed
  (`#[contracterror]`) and returned, so there is no panic-based DoS.
- Positive replay/idempotency protection via state flags; treasury enforces
  quorum + allowlist + per-token cap + balance before transfer.
- `expiry <= release_time` is rejected at creation; `amount <= 0` is rejected everywhere.

**Concerns.**

- **Storage scaling / pagination (mainnet blocker).** Single instance-storage `Map` per
  contract, no per-key persistent entries, `all_ids()` returns the unbounded set. Resource
  cost grows linearly with collection size; large collections risk exceeding Soroban's
  ledger-entry and instruction limits. This is the most important contract-level finding.
- **TTL.** `extend_ttl(5000, 5000)` on all paths (~7 h of ledgers) with no restore helper;
  since all state is in the instance entry, silent archival would freeze the contract.
- **Escrow escape hatch.** Without an explicit expiry, post-`release_time` refund is
  impossible, so an unresponsive counterparty can lock funds indefinitely.
- **Gas measurement.** Contract tests assert behaviour, not resource budgets — no test asserts
  instruction counts or storage bytes. Wasm size and the O(n) storage pattern are the available
  efficiency proxies; per-entry-point instruction budgets (e.g. via `env.budget()`) should be
  added before mainnet.
